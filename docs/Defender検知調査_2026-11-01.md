## 2. 初期調査で確認したこと

対象リポジトリ：`rmatsuoka-jpn/QRReceptionSystem`  
コード調査時点の `main`：[`216d39faed3e14ab9874cc9a6331cba788ed1549`](https://github.com/rmatsuoka-jpn/QRReceptionSystem/commit/216d39faed3e14ab9874cc9a6331cba788ed1549)（2026-11-01）

### 2.1 Gitの履歴とファイル構成

- `main` の直近50コミットを取得して変更概要を確認。表示された範囲で、用途不明のバイナリや実行プログラムを追加する変更は見当たらなかった。ただし、**全履歴を完全監査したわけではない**。
- Gitツリーの再帰一覧を確認。アプリ、関連HTML/CSS/JavaScript、ドキュメント、`vendor/` にあるQRライブラリ・ライセンスで構成される。リポジトリ内に `.exe`、`.bat`、`.ps1` 等のOS実行ファイルは見当たらなかった。**JavaScript自体はブラウザで実行されるコードなので、「実行ファイルなし＝安全」とは言えない**。
- `vendor/qrcode.min.js` と `vendor/html5-qrcode.min.js` は外部ライブラリとして同梱されている。これらを含む全ファイルの依存関係・供給元の完全な監査は未実施。

### 2.2 `app-support.js` の出自

- Git履歴上、最初の追加は [`c1e0887219f5bd61d33890ae7d4bf56b5a0f8077`](https://github.com/rmatsuoka-jpn/QRReceptionSystem/commit/c1e0887219f5bd61d33890ae7d4bf56b5a0f8077)（2026-10-23）。
- 最初のコミット名は **“Add vendored no-network ZIP archive writer and CSV import utilities”**。このコミットで `app-support.js` が新規追加され、当初からオフラインZIP32生成とCSV関連ユーティリティが記述されていた。
- 後続の主な変更：[`4ce3924`](https://github.com/rmatsuoka-jpn/QRReceptionSystem/commit/4ce392479e966d0568756e03203ebd9f137d3fdb)（Excel貼り付け）、[`4827426`](https://github.com/rmatsuoka-jpn/QRReceptionSystem/commit/4827426505b959a6388b926ccd88175a0907985b)（ひな形等）、[`e803606`](https://github.com/rmatsuoka-jpn/QRReceptionSystem/commit/e8036063c3f095b34318e40ae2235c715aa4668f)（貼り付けの区切り文字自動判定）。
- 既知の外部ライブラリをそのまま配置したことを示すヘッダー・配布元記載はなく、**このプロジェクト向けの独自補助コードとみられる**。Git上のコミット作者表示だけでは、AI生成・人手作成・外部サンプル参照の割合は証明できない。

### 2.3 `app-support.js` の機能と静的確認

コードの中心は以下。

1. `zip(files, opts)`：JavaScriptの `Uint8Array` / `TextEncoder` / `Blob` を使って、無圧縮（stored）ZIP32のローカルヘッダー、CRC32、セントラルディレクトリを組み立てる。
2. `pngBytes(dataUrl)`：生成済みPNGのdata URLをバイト列にする。
3. `detectColumn`、`parseCSV`、`parseTSV`、`parsePastedTable`、`detectPasteDelimiter`、`decodeCSV`：CSVやExcelからの貼り付けを処理する。
4. `participation`：受付区分の参加有無を正規化する。

調査した `app-support.js` に、明白な `fetch`、`XMLHttpRequest`、`WebSocket` などの外部通信や、OSのコマンドを起動する処理は見つからなかった。ただし、**これは限定的なコードの目視・文字列調査であり、脅威の不在を保証しない**。

### 2.4 QR一括ZIPとの違い

`app.js` の `exportQRZip()` は、アプリがブラウザ内で生成した次のファイルを `QRSupport.zip()` でまとめる。

- `QR_...png`：対象者ごとのQRカード画像
- `qr_mapping.csv`：参加者ID・氏名・職員番号・所属・グループと画像ファイルの対応
- `README.txt`：配布説明

ここに **Gitのコミット履歴や `app-support.js` 自体は同梱されない**。今回警告されたのは、これとは別のGitHub配布ソースZIP。

### 2.5 ZIP生成処理の限定的な動作試験

`app-support.js` のZIP関数を模擬的な `TextEncoder` / `Blob` とテストデータで実行し、ZIPローカルヘッダー、格納ファイル名・サイズ、セントラルディレクトリ、終端レコードを確認した。テストはPNG相当のダミーバイト列・CSV・TXTの3ファイルで行い、想定したエントリが生成された。

**この試験は、Windows Defenderが検知した実物の `QRReceptionSystem-main.zip` の検査でも、ウイルススキャンでもない。**

## 3. 現時点の評価（事実／推測／未確認を分ける）

**確認された事実**
- Defenderの検知名は `Trojan:Script/Wacatac.B!ml` で、GitHubソースZIP内の `app-support.js` を指している。
- コードはZIP/CSV処理のためのプロジェクト固有の補助スクリプトである。
- 調べた範囲のコード・履歴・ファイル構成に、明白な悪意ある機能や不明な実行ファイルは見当たらなかった。

**考えられる仮説（未検証）**
- Defenderの機械学習・ヒューリスティック検知が独自のZIP生成やバイト列操作などに反応した可能性。
- 正当なコードの**誤検知**の可能性。

**まだ分からないこと**
- 実際にどのバイト列・処理がシグネチャ／判定に一致したか。
- Defenderの定義更新状況、検知された実物ZIPのSHA-256、実物ファイルを別環境で検査した結果。
- Microsoftが当該ファイルを誤検知と正式判定するかどうか。
- リポジトリ全体・同梱ライブラリの本格的なサプライチェーン監査結果。

**したがって「誤検知と断定」「安全と保証」「マルウェアだと確定」のどれも現段階では適切ではない。**

## 4. 次の調査担当者への推奨手順

1. **安全確保を優先**：検知対象は許可・除外しない。Windows セキュリティの保護履歴で隔離／削除などの処理を確認し、必要ならセキュリティ担当と調整する。Defenderのセキュリティインテリジェンスを更新し、適切なスキャンを実施。
2. **証拠を残す**：脅威名、エンジン／定義バージョン、検知時刻、対象ファイル名、ファイルのハッシュ（取得可能で安全な手順による場合）、保護履歴の状態を控える。個人のユーザー名を含むフルパスや参加者データは公開しない。
3. **検知対象の同一性を確認**：警告時点の `main` コミットと、同梱 `app-support.js` のバージョン・内容を比較する。Git blob SHAとファイルSHA-256は異なるため混同しない。
4. **誤検知の正式確認**：Microsoftの[ファイル提出窓口](https://www.microsoft.com/en-us/wdsi/filesubmission)に、組織のセキュリティ方針に従ってサンプルを提出することを検討。提出結果・判定日・回答をこの文書に追記する。
5. **必要に応じた追加監査**：`app-support.js` の静的・動的解析、ZIP生成のテストケース、`vendor/` 内ライブラリの由来・バージョンとハッシュ、GitHubリポジトリの権限・変更履歴を検証する。
6. **改善の検討**：独自ZIP生成処理を保守性・テスト可能性の観点で再評価する。第三者ライブラリへの置換も候補だが、**ウイルス検知を回避する目的で安易に書き換えない**。置換しても誤検知解消の保証はない。
7. **対応後の再評価**：Microsoftの判定結果や解析証拠を踏まえて、運用・配布を続けられるか判断する。

※ 個人情報を含むQR配布ZIPやバックアップJSONを、公開型のファイル解析サイトへアップロードしないこと。GitHub公開のソースZIPと、参加者情報を含むアプリ生成物は区別して扱う。

## 6. 追加調査（2026-11-01 夜・Claude）

> 調査の対象はGitHub上のコードと公開パッケージに限る。**Defender本体での再スキャンは行っていない。** 本章も「安全の保証」や「誤検知の確定」ではない。

### 6.1 検知時点のファイルと現行ファイルは同一

- 検知は 20:45。その時点の `main` は `216d39f`（20:44）で、`app-support.js` を最後に変更したのは `e803606`（19:19）。
- その後のコミット `086fabb` はドキュメントの追加のみ。
- GitHub API でソースZIP（zipball）を取得し、中の `app-support.js` と Git上のファイルを比較したところ、**同一**だった。
  - SHA-256：`4ffab20cd3a602156be6446bbda7172ad16e4a2beafee4781b4a0250a55fb365`
  - サイズ：6,708バイト
- Microsoftに提出する際の照合に使える。
- 注：ZIP全体のハッシュは、取得方法や時刻で変わりうる。

### 6.2 `app-support.js` の全文を確認

- 全102行を目視で確認した。中身は、無圧縮ZIPの作成、PNGのdata URLのバイト変換、CSV／TSVの解析、文字コード判定、○×の正規化のみ。
- 次のものは**ない**：
  - 外部通信：`fetch`／`XMLHttpRequest`／`WebSocket`／`sendBeacon`
  - 動的なコード実行：`eval`／`new Function`
  - `document.write`
  - 外部URL
  - 長いbase64の埋め込み
  - 不可視文字・制御文字
- `atob` は1か所だけ。アプリが生成したQR画像（`data:image/png`）を、ZIPに入れるバイト列に変換する用途で、形式チェック付き。
- 直前の変更 `e803606` は、貼り付けデータの区切り文字（タブ／カンマ）を自動判定する2関数の追加のみ。

### 6.3 リポジトリ全体と履歴

- 全履歴111コミットを取得して確認した。
  - 作者は `rmatsuoka-jpn` と Claude のみ。
  - 追加・削除されたファイルは、現在の18ファイル以外にない。
  - 途中で一時的に入って消えたファイルもない。
- アプリのJS・HTMLにも、外部通信・動的実行・外部スクリプトの読み込みはない。
  - `app.js` 内の外部URLはExcelファイル（xlsx）の書式定義に使う名前空間文字列だけ。
  - `fromCharCode` はExcelの列名（A, B, …）の生成に使っている。

### 6.4 同梱ライブラリは公式配布物と一致

### 6.5 検知理由の推測（未検証）

`Wacatac.B!ml` の `!ml` は、機械学習による判定であることを示す。今回の `app-support.js` は、次のような処理を一つのファイルに含んでいる。

- base64 をデコードしてバイト列にする
- ZIPの「PK」ヘッダーをバイト単位で組み立てる
- `application/zip` の Blob を作る

これは、ブラウザ内でファイルを組み立てて保存させる攻撃手法（いわゆる「HTMLスマグリング」）でよく見られる処理の形と似ている。そのため、**用途が正当なのに形が似ているために反応した**可能性が高いと考える。ただし、どの特徴で判定されたかはMicrosoftにしか確認できない。

### 6.6 推奨する対応

1. **Microsoftへの誤検知申告**（最優先）
   - ファイル提出窓口へ、`app-support.js`（またはソースZIP）を「誤検知の可能性（Incorrectly detected）」として提出する。
   - 中身は公開ソースで、個人情報を含まない。
   - 提出は、組織の方針に従い、まつさんの環境から行う。判定結果はこの文書に追記する。
2. **庁内への共有**
   - 庁内のPC・Webサーバーでも同じ検知が起きる可能性がある。
   - 本番に配置する前に情報システム担当へ共有し、判定が出るまで本番配置は保留する。
3. **切り分け（任意）**
   - 直前の変更（`e803606`）より前の版で検知されるかを確かめる。
   - 例：`archive/4827426.zip` をダウンロードしてみる。
   - 「変更で検知されるようになった」のか、「Defenderの判定モデル更新で検知されるようになった」のかを区別できる。
4. **コードの変更は、判定結果が出てから検討する。**
   - 独自のZIP作成処理を、広く使われるライブラリへ置き換えることは、保守性の観点で検討の余地がある。
   - ただし、検知を回避する目的での書き換えは行わない（第4章の方針どおり）。
